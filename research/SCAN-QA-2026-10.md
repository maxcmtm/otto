# What happens when a prospect types their website into Otto — scan QA, October 2026
Date: 2026-10-02 · Author: Claude Code (QA run + fixes, not committed) · Scope: the landing scan (`landing.html` → `/otto-peek`
→ `otto_api.peek` → `otto_scan.peek`), onboarding steps 1–2 (`onboarding.html` → the same peek, the brand card "as Otto read
it" with Fix), and the create call (`/otto-api/onboard` → `otto_onboard.http_create` → full `otto_scan.scan` → brand,
strategy, plan, trial). Every site in the corpus was read live from this Mac on 02.10.2026; the engine ran in a throwaway
workspace (all `OTTO_*` paths in a temp dir, never the repo's `data.json`).

## TL;DR
- **The scan works on almost every real small-business site, and now reads them correctly.** 59 of 61 corpus sites are read
  (was 56). The 2 left are Cloudflare / bot-walled (flinders.nl, g2.com); the visitor gets a clear "continue and fill in the
  basics" path instead.
- **Before the fixes, half of what Otto showed a Dutch or Irish prospect was wrong or junk.** Every WordPress site showed
  the colour `#003388` (an HTML entity `&#038;` read as a colour), palettes were mostly theme/plugin/payment defaults,
  physio practices were "Education", Huel and a crisps maker were "Education" ("Learn more" buttons), Oatly was "Legal &
  finance" ("Legal" in the footer), names were page titles ("Home • LOT61 Coffee Roasters • Amsterdam"), Dutch sites without a
  `lang` attribute were written in English, and Dutch shops got German or Spanish as a second language from their
  translation links.
- **Two input bugs could hurt the launch directly.** (1) Typing an Instagram/Facebook/Linktree link created a brand called
  "instagram" — and every later Instagram user got "this site is already set up with Otto". (2) The scanner's user agent
  contained "Scan", which common WAF rules block with 403 (thefumbally.ie).
- **What the visitor sees on failure is now specific and says what to do**, in English, Dutch and German: e-mail typed
  ("jan@bakkerij.nl" → reads bakkerij.nl; "jan@gmail.com" → "that's an e-mail address"), social/marketplace page, no such
  domain, parked domain, bot-walled site, file instead of a page.
- **SSRF: no gap found.** localhost, 127.0.0.1, 10.x, 169.254.169.254 (with path), `[::1]`, `0x7f000001`, `localtest.me`
  (DNS → 127.0.0.1), `metadata.google.internal`, `file://`, `ftp://`, `:8080`, `user:pass@` are all refused; the new
  fallbacks (www twin, http, meta refresh) go through the same per-hop guard.
- **Tests**: 25 new regression tests (local fixtures, no network); `tests/simulate.py` exit 0 with no FAIL/WARN; the full
  suite (`python3 -m unittest discover -s tests`, 802 tests) has 801 passing and 1 failure outside the scan, in another
  agent's in-progress ad-video work (`test_copy.AdsTriggers`, see §7). Nothing committed.

## 5. Bugs found and fixed
Engine (`otto_scan.py`, `otto_onboard.py`, `otto_api.py` peek only), with regression tests in the new
`tests/test_scan_inputs.py` (20 tests, local fixture pages) and `tests/test_onboard.py` (`TypedSiteTest`, 5 tests):

1. **Social / marketplace pages became shared brands.** `otto_scan.platform_page()`; refused in `otto_onboard.site_url`
   (create) and `otto_api.peek` (400 `code: platform_page`) before any DNS or fetch.
2. **WAF 403 on the user agent** `…OttoScan/1.0` → `…OttoBot/1.0`. `Accept-Language` follows the country TLD (.nl → Dutch).
3. **`&#038;` / `&#039;` read as colours `#003388` / `#003399`** on every WordPress site → the hex regex never matches after
   `&`; colours now come from CSS only (stylesheets, `<style>`, `style=""`), never JSON blobs or SVG payment icons.

## 6. What is still weak
- **Bot-walled sites can't be read** (Cloudflare challenge, Akamai: flinders.nl, g2.com, bücher.de). The server's full read
  hits the same wall, so "Otto tries again after setup" in onboarding step 1 will usually fail again. Options: a headless
  browser fallback, or ask for 3 screenshots / the Instagram handle in step 2.
- **JS-only sites read thin** (rapanuiclothing.com, excalidraw.com: no headings, fonts or socials in the HTML).
- **No website = no onboarding.** A business that only has Instagram is now told to enter a website (before, it silently
  became brand "instagram"); `create` requires a site. Product decision for Max: allow "I don't have a website" with the
  Instagram handle as identity.
- **Colours are a blocklist** of known defaults: a new theme can still leak its default link colour. Owners can fix in step 2.
- **Industry is a keyword heuristic**: a deli with little text (lilliputstores.com) stays "Unknown"; a café chain that also
  sells beans online (3fe, Butlers) plans as a restaurant. Industry names are English in the Dutch/German UI.
- **Names from the site's own words**: murphysicecream.ie titles itself "murphysicecream.ie"; ad.nl names its publisher
  (DPG Media) in JSON-LD.
- **Speed**: median landing scan ~3 s, p95 ~8 s, a slow WordPress site 20 s (the deadline). The landing shows a spinner on
  "Working out your audience" for that whole time; a counter or "this site is slow" line after ~8 s would help.
- **Country from the browser time zone** when the TLD and currency say nothing: a Dutch `.com` site onboarded from a laptop in
  Israel became country IL. Fine for real customers, confusing in Max's own tests.
- Layout notes for the landing/onboarding owners (not changed here): at 375 px the sticky "Reads / Plans / You approve" pill
  covers the brand-profile header and the scanned-domain tag right after a scan; onboarding's `#site` hash equals the input's
  id, so step 1 opens scrolled past its heading on phones; while a scan runs, the sample bakery profile stays visible under
  the visitor's domain tag.
